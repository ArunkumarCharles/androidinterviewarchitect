It is **an app that teaches**, where code and docs are equally weighted deliverables.## Operating principles1. **Explainability over cleverness.** Prefer the idiomatic, textbook-correct pattern over a clever shortcut, even if the shortcut is shorter. The user needs to be able to say "I chose X because Y" in an interview.2. **Every non-obvious decision gets a comment explaining *why*, not *what*.** E.g. not `// map the flow` but `// distinctUntilChanged here prevents redundant recompositions when the repository emits an unchanged cache value on each DB write`.3. **Show both ends of a tradeoff.** When the project uses MVVM in one feature and MVI in another, the docs must explicitly say which screens use which and why (simple CRUD screen vs. complex multi-event state machine like checkout/feed).4. **Multi-module from the start**, not bolted on later — this is itself an interview topic (system design / modularization strategy).5. **Everything must compile-plausibly.** Use real, current (verify via web search if uncertain) library coordinates, real API shapes (Hilt annotations, Compose Navigation type-safe routes, Room DAOs, WorkManager constraints), not pseudocode. If a library version is uncertain, search rather than guess.## Required tech stack (non-negotiable unless user overrides)| Layer | Requirement ||---|---|| Architecture | Clean Architecture (domain/data/presentation separation) + **both** MVVM (standard CRUD-ish screens) and MVI (complex state-driven screens: feed, checkout) || UI | 100% Jetpack Compose — stateful/stateless composable split, custom `Modifier`s, `derivedStateOf`/`remember`/performance-conscious recomposition || DI | Hilt || Concurrency | Coroutines + Flow — demonstrate `StateFlow` vs `SharedFlow`, hot vs cold streams, structured concurrency || Jetpack | Type-safe Compose Navigation, Room, WorkManager, DataStore, Lifecycle-aware ViewModel || Network/Data | Retrofit or Ktor + OkHttp, sealed `Result`/`Outcome` wrappers, offline-first caching (single source of truth = DB) || Testing | JUnit 5, MockK, Turbine (Flow testing), Compose UI tests || Modularization | Multi-module: `:core:*`, `:data:*`, `:domain`, `:feature:*` at minimum |See `references/tech-stack-checklist.md` for the full per-layer breakdown and rationale to cite when generating code and docs — read it before scaffolding modules.## WorkflowWork in this order; don't skip to code before the shape is agreed, but don't over-interview someone who has clearly already specified everything (the trigger prompt usually has).1. **Confirm scope** (skip if already answered in the prompt): what should the sample domain be (e.g. a social feed + checkout, a note-taking app, a movie catalog)? Default to something with a natural "feed" (MVI candidate) and a natural "settings/profile" or "form" screen (MVVM candidate) plus a "checkout"/multi-step flow (MVI candidate) if not specified — this maximizes pattern coverage.2. **Output the project structure first**, as a tree, before any code — module boundaries, package-per-module, and a one-line purpose per module.3. **Generate core implementation files module by module**, following the data flow: `DataSource → Repository → UseCase → ViewModel → UI`. For each file, include the "why" comments described above. Prioritize breadth (one clean example of each pattern) over exhaustively fleshing out every CRUD screen — this is a teaching artifact, not a shipping product.4. **Generate tests** for at least one ViewModel (MVVM), one MVI reducer/state-machine, one Repository (offline-first behavior), and one Compose UI test — enough to demonstrate the testing approach, not full coverage.5. **Write the documentation** (see below) last, once the code exists to reference concretely.6. **Use `create_file`/the docx or md skill and the computer** to actually produce the files under `/mnt/user-data/outputs` rather than only pasting code inline — this is a multi-file project and the user will want to browse/download it. Use a `.md` architecture doc (or ask if they want a `.docx`) rather than dumping everything into chat.## Documentation requirementsThe docs are as important as the code. Produce (as one architecture doc, or split into README.md + ARCHITECTURE.md):- **System design overview**: text-based (or Mermaid) diagram of module dependencies and the Clean Architecture layers, C4-style (context → containers → components) is a good frame but plain text/ASCII + Mermaid is fine — don't over-format.- **Data flow walkthrough**: concretely trace one read path and one write path through `DataSource → Repository → UseCase → ViewModel → UI`, naming the actual classes/functions generated, not generic placeholders.- **MVVM vs MVI rationale**: a table or section explicitly stating which screens use which pattern and the tradeoff that motivated it.- **Interview Cheat Sheet** (this is the centerpiece — do not omit or shrink it): a table or Q&A mapping common senior/staff Android interview questions to *exactly where in this codebase* the answer lives. Cover at minimum:    - How is UI state handled, and why `StateFlow` over `LiveData`/`SharedFlow` where used?    - How are configuration changes and process death handled (`ViewModel` scoping, `SavedStateHandle`, DataStore)?    - How does the offline-first caching strategy work end to end?    - How is dependency injection scoped (`@Singleton`, `@ViewModelScoped`, `@ActivityRetainedScoped`)?    - How is navigation type safety achieved, and why does it matter?    - How would you test the reducer/ViewModel in isolation (mention MockK + Turbine specifics)?    - How and why is the project modularized this way — what does it buy at scale / for build times / for team ownership boundaries?    - Where is `derivedStateOf` used and what recomposition problem does it solve there?    - Feel free to add more questions the generated code naturally surfaces (WorkManager constraints, DataStore vs SharedPreferences, hot vs cold flows, sealed class `Result` wrapper vs exceptions).See `references/doc-structure-template.md` for a ready-to-fill outline of README/ARCHITECTURE/cheat-sheet sections if useful, but adapt freely to the actual generated project rather than filling it mechanically.## Scope calibrationThis is a large ask. If the user's request is broad ("build the whole thing"), it's fine to generate it in stages across the conversation (structure → module A → module B → tests → docs) rather than trying to emit everything in one giant response — flag that you're doing this and keep momentum rather than stalling on scope questions the prompt already answered.
