# Senior / Staff Android Interview Cheat Sheet

This cheat sheet maps common senior and staff architectural interview questions directly to where the implementation lives in this codebase.

| Interview Question | Codebase Reference | Expert Answer / Rationale |
|---|---|---|
| **How is UI state handled across configuration changes?** | `FeedViewModel.uiState` (`StateFlow`) | `StateFlow<FeedUiState>` is hot, conflated, and always holds the latest state. It survives configuration changes because the ViewModel survives activity recreation via `ViewModelProvider`. |
| **How do you handle process death and persistence?** | `CheckoutViewModel` + `SavedStateHandle` | `SavedStateHandle` injects state survival across process death (when Android kills the process in background) without manual `onSaveInstanceState` boilerplate. |
| **How does offline-first caching work end-to-end?** | `PostRepositoryImpl` (`:core:data`) | Room is established as the Single Source of Truth (SSOT). The repository exposes a reactive `Flow` from Room, fetches remote data in the background, upserts into Room, and the UI observes DB changes reactively. |
| **Why does the domain layer use no Android APIs?** | `:domain` module | Keeps business logic free of framework types, testable in milliseconds on the JVM without robolectric/Android mocks, and decoupled from framework lifecycle changes. |
| **How is DI scoped in Hilt, and why?** | `DatabaseModule`, `NetworkModule`, ViewModels | `@Singleton` for expensive shared singletons (Room DB, OkHttp/Retrofit). `@ViewModelScoped` for use cases / stateful dependencies bound to ViewModel lifecycle. |
| **How is type-safe navigation achieved?** | `MainActivity.kt` & feature routes | Kotlin `@Serializable` objects replace legacy string-based route arguments, providing compile-time safety and type-safe argument passing. |
| **How do you unit test MVI ViewModels and Reducers?** | `FeedViewModelTest.kt` | Use JUnit 4, MockK (`coEvery`), and Turbine (`test { awaitItem() }`) to assert asynchronous `StateFlow` emissions deterministically without Dispatchers main thread locking. |
| **Why modularize this way (Clean Arch + Multi-module)?** | Project module tree (`:core:*`, `:domain`, `:feature:*`) | Enforces architectural boundaries, prevents feature-to-feature coupling, enables parallel compilation/build speedups, and clarifies team ownership. |
| **When would you use `SharedFlow` vs `StateFlow`?** | Event vs State channels | `StateFlow` is for UI state (hot, conflated, retains latest value). `SharedFlow` (or `Channel`) is for one-shot UI events (navigation, snackbars, toasts) that should not be replayed on configuration change. |
| **How do you ensure reliable background tasks?** | `CacheSyncWorker` (`:core:data`) | `WorkManager` guarantees execution even across app restarts, with explicit constraints (`NetworkType.CONNECTED`, `requiresBatteryNotLow`). `@HiltWorker` + `ArchitectApplication`'s `Configuration.Provider`/`HiltWorkerFactory` let the worker receive constructor-injected dependencies. |
| **How do you unit-test offline-first repository behavior?** | `PostRepositoryImplTest.kt` (`:core:data`) | MockK fakes for `PostDao`/`ApiService`/`UserPreferencesDataSource`; Turbine asserts the Room snapshot is emitted *before* the network call resolves, that a network failure still yields cached `Result.Success` (not `Result.Error`), and that a locally-liked post survives a sync where the network reports it unliked. |
| **How do you stop unnecessary recomposition in Compose?** | `TopicScreen.kt` (`items(..., key = { it.id })`, immutable `Topic`) | Compose skips a composable when its params are stable and unchanged. Use immutable data classes, stable keys in lazy lists, hoisted state, and `derivedStateOf` for computed values; confirm with compiler metrics. |
| **`remember` vs `rememberSaveable`?** | Expanded state in `TopicViewModel.expandedTopicIds` | `remember` survives recomposition only. `rememberSaveable` (or ViewModel/`SavedStateHandle`) also survives rotation and process death. Here the expanded set lives in the ViewModel so it survives configuration change without a Bundle. |
| **Why collect with `collectAsStateWithLifecycle`?** | `TopicRoute` / `FeedRoute` | It stops collecting below `STARTED`, so upstream Room/network flows are not kept hot while the app is backgrounded, saving battery and work. |
| **How do you combine several data sources into one UI state?** | `TopicViewModel.loadTopics()` (`combine`) | `combine` of topics, questions and a local `MutableStateFlow` of expanded ids yields one immutable `TopicUiState.Success`, so the UI has a single source of truth and toggling a card never re-queries the DB. |
| **How do you choose coroutine dispatchers and keep tests deterministic?** | ViewModel tests using `Dispatchers.setMain` | Main for UI, IO for blocking work, Default for CPU work. Inject dispatchers (or set Main in tests) so a `StandardTestDispatcher` controls scheduling. |
| **How does cancellation work with structured concurrency?** | `viewModelScope.launch` in `TopicViewModel` | Children are bound to the parent scope, so clearing the ViewModel cancels all work. Never swallow `CancellationException` in a broad `catch`; rethrow it. |
| **How do you handle Room schema changes?** | `AppDatabase` (version 2) + `DatabaseModule` | Bump the version, write an explicit `Migration`, export schemas, test with `MigrationTestHelper`. This sample registers `MIGRATION_1_2` and uses `fallbackToDestructiveMigrationOnDowngrade()` only for downgrades, so a user's likes survive an upgrade. |
| **How do you model a one-to-many relationship in Room?** | `QuestionEntity` (FK to `TopicEntity`) | A foreign key with an index on the child column and `onDelete = CASCADE`. Use `@Upsert`, not `REPLACE`, on the parent: REPLACE deletes then inserts, which cascades and wipes the children. |
| **How do you populate a database on first launch?** | `DatabaseModule` `RoomDatabase.Callback.onCreate` + `SeedData.kt` | Insert seed rows in `onCreate` (parents before FK children) so offline-first screens have content with no backend. Use stable string ids so a later network sync upserts over them. |
| **What does a good testing pyramid look like on Android?** | `FeedViewModelTest`, `UseCaseTest`, `MappersTest`, `PostRepositoryImplTest`, `QuestionRepositoryImplTest`, `TopicViewModelTest`, `FeedScreenTest` | Many fast JVM unit tests (ViewModels, repositories with MockK fakes + Turbine), fewer integration tests, and a thin layer of Compose UI tests. The pure-Kotlin domain layer keeps the base cheap. |
| **How do you send a snackbar/toast without replaying it on rotation?** | `TopicViewModel.events` + `TopicScreen` `LaunchedEffect` | `Channel(BUFFERED).receiveAsFlow()`: each event is consumed exactly once. `StateFlow` would replay the last value after rotation and re-show the snackbar. |
| **How do you build debounced search?** | `TopicViewModel.observeContent` | `MutableStateFlow<String>` → `debounce` (0 for empty so first paint isn't delayed) → `distinctUntilChanged` → `combine` with data. The text field keeps its own local text so debounced state never eats keystrokes. |
| **What does `derivedStateOf` buy you?** | `FeedScreen.kt` (scroll-to-top FAB) | Scroll position changes every frame; the derived Boolean flips only at a threshold, so only the FAB recomposes, not the list host. |
| **Why are use cases `@ViewModelScoped`?** | `domain/usecase/*` | One instance per ViewModel, shared by anything in that ViewModel, released with it. Avoids a singleton holding state across screens. |
| **How do you page an offline-first list?** | `PostRepositoryImpl.getPagedFeed`, `PostRemoteMediator` | Page over Room's `PagingSource` (auto-invalidates on writes); the `RemoteMediator` only refreshes Room from the network. Errors surface as `LoadState.Error` while cached pages stay visible. `cachedIn(viewModelScope)` survives rotation. |
| **How do you migrate a Room schema without losing data?** | `Migrations.kt`, `AppDatabaseMigrationTest` | Export the schema, write an explicit `Migration` whose SQL matches it, and test by opening a real old-version DB through Room (validates the result). `fallbackToDestructiveMigration` would wipe user state. |
| **Why inject dispatchers?** | `DispatchersModule`, `*RepositoryImplTest` | Hard-coded `Dispatchers.IO` can't be controlled in tests. Qualified injection lets tests pass a `TestDispatcher`. |
| **How do you unit-test a WorkManager worker?** | `CacheSyncWorkerTest` | `TestListenableWorkerBuilder` with a custom `WorkerFactory`; drive `setRunAttemptCount` to assert retry-vs-failure policy. |
| **How do you avoid a theme flash on cold start?** | `MainViewModel.themeMode`, `MainViewModelTest` | Expose the persisted theme as a `StateFlow` with an initial `"system"` value and `stateIn(WhileSubscribed(5_000))`. The first frame follows the OS setting, then switches once DataStore emits. The 5s timeout keeps the upstream alive across a rotation. |
| **How do you test a repository that fakes latency, like checkout?** | `CheckoutRepositoryImplTest` | `runTest` runs `delay(1500)` in virtual time, so the test is instant. The decline path is deterministic (card ends in `0000`) rather than random, so both outcomes are asserted reliably. |
